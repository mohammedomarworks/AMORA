## Evidence and status rules

**Complete** means equivalent user behavior exists and has passed applicable tests plus real Windows verification. **Partial** means real code exists but behavior, integration, coverage or real-machine verification is incomplete. **Missing** means there is no equivalent production implementation. **Blocked** means a specific API/platform/dependency prevents that implementation. A test name below is evidence of intended coverage, not a test-run result. Preview services, declared enums and buttons are not functional parity.

Paths in the matrix use these unambiguous repository-relative prefixes:

- `M/` = `Sources/AMORA/`; `MT/` = `Tests/AMORATests/`.
- `W/` = `Windows/AMORA.Orbit/`; `WT/` = `Windows/AMORA.Orbit.Tests/`.

The user-supplied image is the Windows visual authority. It shows a narrow camera-area capsule and a wide shallow expanded island: black top strip with navigation and cyan indicator, charcoal companion area on the left, suggestion strip above a two-column media/timer and battery/system grid on the right. It is not a permanent tall dashboard. Mac `M/UI/WideIslandView.swift` agrees with this composition: companion width 220 points, real shared timer/music/assistant state and separate page content. `M/UI/DynamicIslandView.swift` defines collapsed/quick/workspace states, defaults 200×40, 840×230 and 960×680. `M/Core/WindowManager.swift` adapts quick size around 760–900×190–250, anchors to display top, and animates one window. Windows should preserve the composition while adapting clearance/DPI to real Windows displays.

### Implementation notes

The baseline matrix above is preserved so implementation gaps are traceable. Current edits address A1–A4, B1, F1–F2 and G1–G2 without promoting them to full parity:

- Native shell: 176×34 DIP compact and 860×300 DIP quick home, separately selected 520-DIP workspace; retained HWND, bounded DPI geometry, same-monitor fullscreen suppression, display-change recovery, reduced-motion-aware transition and working tray icon/settings recovery. Coverage added in `WT/OrbitWindowLifecycleTests.cs` and expanded `WT/PositioningServiceTests.cs`.
- Power/telemetry: SystemStatusViewModel now calls native services' Refresh before reading snapshots every two seconds, dispatches bound notifications to the UI, catches expected cancellation and ignores queued work after disposal. GetSystemPowerStatus failure/unknown is explicitly unavailable; only a no-battery flag with known AC is desktop power. CPU requires two valid advancing samples; API failure/reset does not fabricate 0% load. Memory sampling validates physical totals. Context summaries preserve unavailable power rather than calling it desktop AC. `WT/LiveSystemStatusTests.cs` adds seven focused regressions for these failures, sampling and dispatcher/disposal behavior.
- Automation changes are not an exactly-once transaction with an external player. A durable reservation is written before the action, so a process crash can lose that occurrence but cannot silently replay it on restart. Post-action result-write failure is reported as “action ran, result could not be saved”; a failed pre-action reservation executes nothing. This favors avoiding duplicate side effects. Recurring missed schedules are skipped/rescheduled; expired one-time schedules are disabled. The service does not yet support multiple concurrent AMORA processes sharing the same store.
- Explicit reminders do not enable proactive suggestions. Later occurrences have distinct identities; disabling proactive suggestions does not hide an explicit reminder, and completing an earlier asynchronous suggestion cannot dismiss a newly arrived reminder. Native notification/toast delivery is not claimed.
- Clipboard monitoring subscribes only after explicit enable and only captures future changes. Disabling or clearing cancels pending reads; disabling/exit clears local history. Native registered privacy formats are checked before requesting the WinRT data package, then AvailableFormats is inspected before text. Restores are marked private and excluded from Windows history/cloud sync. Structured credentials/private keys are additionally rejected without treating discussion of privacy markers as a secret. No code calls Windows clipboard history retrieval or collects files/images/window contents.
- Mac sources remain unchanged. Implementation and test evidence does not replace the actual application/ZIP acceptance below.

## Platform decisions

- WinUI 3/C# remains the native architecture. Windows GSMTC replaces Mac AppleScript transport for participating players; capabilities and source identity must come from actual sessions. This does not provide the browser native messaging protocol or guarantee all installed players support every operation.
- Windows top-edge placement is an adaptation. Do not assume a hardware camera notch, reserve an invisible large input window, or place the application over fullscreen content by default.
- Apple FoundationModels cannot be ported as an API. Windows offline support requires a real inference runtime; the existing LocalStubAIProvider is not that runtime.
- Windows clipboard privacy differs from Mac: the adapter rejects the presence of `CanIncludeInClipboardHistory` and `CanUploadToCloudClipboard` conservatively even when their DWORD could be one, avoiding delayed-rendered marker payload reads. This can omit safe content from apps that explicitly opt into Windows history. It also rejects Mac-style concealed/transient/autogenerated formats and `ExcludeClipboardContentFromMonitorProcessing`. The marker names/semantics and restore API are documented by Microsoft in [Clipboard formats](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats#cloud-clipboard-and-clipboard-history-formats) and [SetContentWithOptions](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.datatransfer.clipboard.setcontentwithoptions). Third-party applications must expose privacy markers for marker-first protection; the additional structured-secret filter is conservative, not a guarantee of detecting every sensitive text. Clipboard history remains separate from cloud prompts and persistent memory.
- Mac automation recovery catches up missed work, while baseline Windows skips/reschedules it. Changing that policy requires bounded, deterministic semantics and explicit UI documentation, never unexpected bursts after restart.
